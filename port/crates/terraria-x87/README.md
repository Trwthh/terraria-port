# terraria-x87

`System.Math` with the results of the original game: 32-bit .NET Framework 4 (CLR 4.0.30319, legacy x86 JIT), x87 FPU, control word
`0x027F` (53-bit precision, round to nearest). Std only, no dependencies. The float-precision rule of the same JIT is in
[FLOAT_RULE.md](FLOAT_RULE.md).

```
cd port
CARGO_TARGET_DIR=target-x87 cargo test -p terraria-x87 -j 3 -- --nocapture --test-threads 1
```

The tests read `refdata/worldgen/x87*` and `float_probes` (a missing file is skipped with a message) and print the report below.

## 1. How the runtime computes each function (evidence, then implementation)

Evidence: the import table of `C:\Windows\Microsoft.NET\Framework\v4.0.30319\clr.dll` lists `_CIacos _CIasin _CIcosh _CIexp _CIfmod
_CIlog _CIlog10 _CIpow _CIsinh _CItanh ceil floor` from `ucrtbase_clr0400.dll` and nothing for sin, cos, tan, atan, atan2, sqrt: those are
x87 instructions emitted inline. Raw instruction results were dumped next to `System.Math` results (`refdata/worldgen/x87_raw`, 80-bit
register values from machine-code thunks): for all 244,000 + 244,000 + 244,000 + 170,000 + 220,000 records
`Math.Sin/Cos/Tan/Atan/Atan2(x)` equals the instruction's register value rounded to double (Atan2 except two infinite operands).

| functions | what the runtime runs | what this crate does | status |
|---|---|---|---|
| `sin` `cos` `tan` | `fsin` `fcos` `fptan` + pop | `trig.rs`: exact `r = x - k * p66/2` with the instruction's 66-bit pi (`p66 = 0xC90FDAA22168C234C * 2^-66`), true sin / cos of `r` in quadrant `k mod 4`, correctly rounded to the 64-bit register, then to double. `abs(x) >= 2^63`: operand returned unchanged (`tan`: NaN, the pop empties the stack). sin / cos: 128-bit fixed point (`Q2.126`, error below 2^-58 of a register ulp, 320-bit fallback when the rounding is too close to call); tan: 320-bit fixed point | not provably exact, see section 3 |
| `atan` `atan2` | `fld1; fpatan` / `fpatan`; the CLR returns NaN when both operands are infinite | `trig.rs::fpatan`: every special case of the instruction, true pi, 320-bit fixed point, correctly rounded to the register | not provably exact, see section 3 |
| `sqrt` `abs` `round` | `fsqrt` (honours the precision control) `fabs` `frndint` | IEEE operations | exact |
| `floor` `ceiling` `truncate` `sign` `min` `max` `round_digits` `round_away` `round_digits_away` `ieee_remainder` `fmod` | C runtime `floor`/`ceil`/`modf`, `fprem` loop, managed code of mscorlib | the same statements in Rust (`lib.rs`) | exact |
| `pow` `log` `log10` `acos` `asin` `exp` | `_CIxxx` jumps to an SSE2 routine when SSE2 is present and MXCSR / the x87 control word have all exceptions masked (always true in the CLR). Table driven, about 0.5 ulp, not correctly rounded. `Math.Pow` first applies the CLR's NaN / `(+-1, +-inf)` rules | `crt_sse2_gen.rs`: instruction-by-instruction transliteration of those routines on a small register machine (`crt_cpu.rs`), generated by `tools/refdump_worldgen/crt_sse2/gen_crt_sse2.py`; tables copied from the DLL | exact |
| `sinh` `cosh` `tanh` | `_CIsinh` etc.: x87 routine built on `f2xm1` / `fscale` (not SSE2) | correctly rounded value from 320-bit fixed point | approximate |

`Math.Round` overloads the game uses (grep over `decompile/Terraria`): `Round(double)` 95 times and `Round(double, int)` once
(`Math.Round(Position.Y, 2)`); `MidpointRounding` never. Both overloads and the away-from-zero ones are implemented and tested.

Results that stay in a register: `sin_ext` `cos_ext` `tan_ext` `atan_ext` `atan2_ext` return the 80-bit register value (`F80`).
`Math.Sin(x) * y` multiplies THAT value: on 20,000 records the model "register value times y, rounded to 53 bits" misses 1, the model
"double result times y" misses 4,735 (`x87_more/SinMul`; the same for CosMul, SinAdd, TanMul, AtanMul, Atan2Mul3 and for `double s =
Math.Sin(x); double c = Math.Cos(x); return s * y + c;`, where the two double LOCALS keep the register values). Use
`sin_ext(x).mul(F80::from_f64(y), 53).to_f64()` for such expressions and `sin_f32` etc. for `(float)Math.Sin(x)` (one rounding from the
register to float). `pow`, `log`, `acos`, `sqrt` return plain doubles (`x87_more/PowMul`, `SqrtMul`: exact with double arithmetic).
Doubles otherwise carry no extra precision: `x87_more/DblLocal` and `DblField` (the same expression with a double local / a static
double field) both equal IEEE arithmetic on all 20,000 records. Not covered: results in the subnormal range or beyond `f64::MAX` held
in a register (the register has a wider exponent range).

## 3. What is not exact, and why

**Since 2026-10-16 the x86 / x86_64 builds execute the instructions themselves** (`src/hw.rs`: `fsin`, `fcos`,
`fptan` + pop, `fpatan` in inline assembly, the 80-bit register stored with `fstp tbyte`): the original game returns the
CPU's own results on the CPU it runs on, so the port does too, and the last-bit cases below disappear on any x86
machine (the gallery and interaction reference runs had dust velocities through `Utils.RotatedBy` that showed them).
The model stays the definition where there is no x87 (the browser build) and with `TERRARIA_X87_TRIG=model` (read
once; `hw::set_enabled` for tests). The tests check the instructions against the raw tables (`x87_raw`: Fsin, Fcos,
Fptan, Fpatan1 identical on the reference machine). What follows describes the model.

**fsin / fcos / fptan / fpatan depend on the processor.** The tables come from one CPU (AMD Ryzen 5 7600X). The instruction is
specified up to an error below one unit of the 64-bit significand. This CPU's microcode returns the correctly rounded register value
in 97 to 99% of the calls and the neighbouring one otherwise (measured error up to 0.54 ulp for fsin / fcos, 0.64 ulp for fptan /
fpatan). The crate returns the correctly rounded one. The two differ after rounding to double only when the register value sits next to
a rounding boundary of the double: about 1 call in 100,000 (31 of 4.5 million dense records for sin / cos, 8 of 1 million for tan /
atan / atan2), always by one ulp. Every mismatch in every table is of that kind; the tests assert it (the reference equals the
double obtained from the model's register value plus or minus one unit) and bound the count at 100 per million. Removing the residue
would need the microcode's internal algorithm (the error pattern suggests polynomial evaluation in a format with about 68 significant
bits); a table of corrections was ruled out. On another CPU model the set of affected arguments is different; on Intel processors the
last-bit behaviour of these instructions is known to differ from AMD's. What does not depend on the CPU: the 66-bit pi reduction
(`Math.Sin(Math.PI) = 1.2246063538223773e-16`), the out-of-range rule (`Math.Sin(1e22) = 1e22`), special values.

**sinh / cosh / tanh** are several x87 instructions in a row inside the C runtime; the crate returns the correctly rounded value, which
is 1 ulp off in 0.02% (tanh) to 2.2% (sinh / cosh, mostly for abs(x) > 100) of the records. The game does not call them.

**The fallback of the fast path.** sin / cos decide the rounding from a value with an error below 2^-58 ulp and fall back to 320-bit
arithmetic (error about 2^-180 ulp) when closer than 2^-54 ulp to a boundary; the 320-bit result is rounded without a further check.
A result within 2^-180 ulp of a boundary does not occur for these functions on double arguments, but there is no proof of it.

## 4. The transliterated C runtime routines

`crt_sse2_gen.rs` is machine-generated from `C:\Windows\SysWOW64\ucrtbase_clr0400.dll` (32-bit, sha256 `32399951...b5e7149`, recorded in
the file header): every reachable instruction of the SSE2 routines behind `_CIpow` (647 instructions), `_CIlog` (140), `_CIlog10`
(144), `_CIacos` (303), `_CIasin` (314), `_CIexp` (148) becomes one Rust statement with the original instruction as a comment; the
constant tables (38 KB of the image) are embedded. Two short x87 runs in `_CIexp` (scaling at 64-bit precision) are replaced by a
helper (`crt_cpu::ext_mul_add_mul`); the error-support routine is modelled by its effect on the return value. It is exact because it is
the same sequence of IEEE operations, not because it was tuned. Two things to know: the file is derived from a Microsoft binary (the
routines are Intel LIBM code), which matters if the port is ever distributed; and another build of the DLL may differ (the generator
prints a warning when its two patch sites do not match and records the hash).

## 5. Files

`src/lib.rs` public functions, `f80.rs` register value and its roundings, `hw.rs` the processor's instructions, `trig.rs` the model of the x87 instructions, `big.rs` 320-bit fixed point,
`consts.rs` constants, `crt_cpu.rs` + `crt_sse2_gen.rs` C runtime routines, `tests/tables.rs` the report above, `tests/probes.rs` the
three trigonometric float probes (P25, P26, P30: 2000 / 2000 each).
